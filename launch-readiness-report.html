P0 — launch blockers

These lose data or publish AI text without review. At 10 businesses or 10,000, you don't launch with these open.

01Fixeddone

The reviews→analytics pipeline is dead whenever Kafka is running

Fixed: outbox worker now wraps payload as {"event_type": ..., "payload": ...} so the analytics consumer dispatches correctly. Consumer calls commit() after each message. Pushed as eb99563.

The outbox worker sends the bare event payload to Kafka, but the analytics consumer dispatches on an event_type field inside the message value. It finds nothing, logs "unrelated event type" at debug level, and drops the event — while the outbox row is marked sent, so it never retries. Every review that arrives through the normal (Kafka-up) path gets no insight row, no sentiment, no rollups, no replied-tracking. The pipeline only works today in the Kafka-down fallback path, which wraps events correctly.

  • outbox/worker.py:110 — sends json.dumps(event.payload)
  • analytics/consumer.py:371-374 — expects event.get("event_type") in the value
  • analytics/consumer.py:398-435 — the fallback path that wraps correctly
FixWrap the Kafka value as {"event_type": …, "payload": …} in the outbox sender (or make the consumer unwrap bare payloads), then run one end-to-end test with Kafka up: new review → ReviewInsight row appears.
02Fixeddone

Kafka offsets are never committed — every deploy replays the entire topic

Fixed: consumer now calls consumer.commit() after each message reaches terminal state. Pushed as eb99563.

The consumer is created with enable_auto_commit=False but never calls commit(). Combined with auto_offset_reset="earliest", every restart or rebalance re-reads the whole retained topic. Handlers are idempotent so results stay correct, but the replay itself becomes your deploy-day load event, and it grows with topic age.

  • kafka/client.py:80 — enable_auto_commit=False
  • analytics/consumer.py:463-466 — the loop with no commit
FixCommit the offset after each message reaches durable terminal-or-retry state — the exact rule the consumer design doc already states.
03Blocker~1 day

Inbound WhatsApp/Instagram/Facebook messages are silently lost on worker restart

The meta-events worker claims a message by setting status processing and committing — and never reclaims it. The code comment says lease management is skipped "until migration adds the columns", but that migration already shipped. A worker crash or redeploy mid-message leaves inbound customer messages stuck in processing forever. For a messaging product this is the most user-visible failure possible.

  • channels/meta_events_worker.py:107-110 — "we skip lease management"
  • modules/jobs/ runner already has the expired-lease reclaim pattern to copy
FixReuse the JobRunner lease-expiry reclaim: on startup and periodically, reset stale processing rows past the lease deadline back to pending.
04Blocker · decisionhours

AI replies auto-post to Google by default — and ignore the engine's own "needs review" verdict

approval_mode defaults to auto, so every 4–5★ review gets an AI-generated reply posted live with no human in the loop. Worse: when the reply engine itself flags a draft as needs_review (off-topic, failed validation), the worker never checks that flag — the post decision is made purely from rating + mode, so flagged replies still go out on a 4★ review. This is public, brand-facing, unreviewed AI content on day one.

  • channels/models.py:446-451 — approval_mode default "auto"
  • channels/reviews_worker.py:653-697 — posts on rating + mode only
  • review_engine/service.py:532-538 — the needs_review verdict nobody reads
FixFlip the default to approval and make the worker refuse to auto-post any draft whose engine verdict is needs_review. Merchants who want full auto can opt back in, knowingly.
05Fixeddone

Localith sync re-enqueues every review of every listing, every 60 seconds

Fixed: gated re-enqueue on enrichment status + unchanged content (same check as native reviews_worker path). Sync interval raised from 60s to 300s. Pushed as 1733eef. Note: Localith being replaced by Google API at launch — fix ensures no 200k outbox rows/min waste in the interim.

The third sync loop enqueues review.discovered for all items with no done/content gate, and the fetch pulls full review history every pass — each event its own INSERT and commit. At 1000 listings × ~200 reviews that is on the order of 200k outbox rows per minute. It buries the outbox, Kafka, and the consumer long before you reach 1000 businesses; even at 50 businesses it's measurable waste.

  • localith/service.py:1243-1275 — the ungated loop
  • embedsocial.py:194-208 — fetch_all_items pulls all reviews every pass
  • reviews_worker.py:253-267 — the native path's gate, to mirror
FixGate the re-enqueue on enrichment status + unchanged content (same check the native path uses), and raise the sync interval — reviews don't need a 60-second SLA.
06Blocker · ops1–2 days incl. rehearsal

There is no backup story beyond "RDS PITR, configured in the console" — and it has never been rehearsed

Zero pg_dump tooling, no restore runbook, Kafka and Redis on unbacked single-box volumes. The checklist notes two migration incidents have already happened. One bad migration on an unrehearsed-restore database is the business-ending scenario, and it's fully preventable inside the timeline.

FixTurn on RDS PITR now, add a nightly pg_dump to the existing S3 bucket with 30-day retention, and actually rehearse one restore into a scratch database. Write the runbook down.

P1 — scale & production gaps

Fine at 10 businesses; each of these hurts on the way to 1000.

The honest scaling statement: the current single t3.small box (api + worker + Redis + single-broker Kafka + Caddy) will comfortably serve your launch cohort of ~10 businesses. It will not serve 1000 — not because of raw capacity, but because items 07–13 below turn into incidents: throttled shared API keys, invisible dead channels, and a worker that physically cannot scale out (container_name in the compose file blocks --scale).

07Scale~1 day

Google channels are never marked expired, and there is no 429/backoff handling

A merchant who revokes access in their Google account keeps channel status active forever; the poller re-fails every 5 minutes indefinitely and the UI never prompts reconnection. And the Google client handles only 401-retry-once — no 429/Retry-After, no backoff, no per-channel cooldown.

  • channels/google_reviews.py:256-285 — _authed_request, 401-only
  • channels/meta/oauth.py:102 — the expired-write that exists for Meta but not Google
FixRepeated refresh failure → mark channel expired + notify merchant to reconnect. Add backoff with a per-channel error cooldown.
08Scale · concentrationdecision + config

All tenants ride one shared Localith/EmbedSocial API key

Per-tenant keys exist but are optional; by default every business syncs through one provider account. That account is a single point of failure and the first thing EmbedSocial throttles — and with the 60-second sync interval, you'd be the one triggering it.

FixDecide the launch posture: mandate per-tenant keys at onboarding, or negotiate provider limits and keep the shared key with monitoring + the interval raise from blocker 05.
09Scale~1-2 days

The review poller is serial and fetches one page of 50 reviews

One asyncio task processes all due channels sequentially; per new review that's LLM calls + posting + up to 6s of read-back sleeps. At 1000 channels a pass takes hours. And list_reviews has no pagination loop — a business with a >50-review burst silently loses the overflow. The atomic lease does allow running N worker instances; nothing stops you adding replicas except the compose file.

  • channels/reviews_worker.py:742-754 — sequential pass
  • channels/google_reviews.py:396-397 — single page of 50
  • docker-compose.prod.yml:86 — container_name blocks --scale
FixBound a small worker pool over claimed channels, add the pagination loop, drop container_name so 2-3 worker replicas can share the load.
10Scale · quality2-3 days or descope

RAG vector search is structurally blind past ~90 chunks — and keyword search doesn't work in Arabic/Urdu

Vector search loads only the first top_k*3 chunks ORDER BY seq and does pure-Python cosine over that prefix; embeddings live in JSON text columns with no pgvector. Any databank bigger than ~90 chunks has most of its content invisible, silently. The keyword half is to_tsvector('english') computed on the fly, with no GIN index and no usefulness for Arabic or Urdu — your core languages.

  • rag/search.py:17-51 — the prefix-window cosine
  • rag/models.py:70 — embeddings as JSON text
FixDecide by day 10: migrate to pgvector (best), or descope honestly — cap databank sizes, widen the window, and add an Arabic-aware keyword side — and adjust the marketing claim to match. A silent recall collapse is worse than a smaller feature.
11Quality~half day

Enrichment failures are invisible — LLM failures silently store heuristics as "done"

enrichment_status="failed" is never written anywhere. When the LLM call fails, the catch returns a deterministic heuristic and the row is stored as done, indistinguishable from real LLM output. There is no retry, no DLQ, and no way to know enrichment quality degraded — free-plan tenants hit this on every review via the 402 budget path.

  • analytics/enrichment.py:174-176 — catch → heuristic
  • analytics/enrichment.py:28 — hardcoded groq model, bypassing admin model curation
FixWrite the failed status with a retry count, surface it in admin stats, and add one retry before falling back to heuristics.
12Infra1-2 days

Single small box, Kafka replication factor 1, and monitoring that exists in code but isn't switched on

One OOM kills api, worker, Redis, and Kafka together; Kafka RF=1 means a broker disk issue pauses the whole pipeline; Redis (fail-closed auth) has 128 MB and no memory alarm — a full Redis is a total login outage. Meanwhile /metrics is served but scraped by nothing, and GlitchTip DSNs default to empty, so error tracking is off. You will learn about outages from customers.

  • docker-compose.prod.yml:123,133-157 — Redis noeviction, Kafka RF=1
  • deploy/env.prod.example — empty GlitchTip DSNs
FixFor launch: fill the DSNs, point any hosted uptime monitor at /readyz, scrape /metrics with even a single-node Prometheus, add a Redis memory alarm. Worker on its own box removes the shared-OOM risk. Kafka RF=1 is acceptable at launch if documented; revisit for 1000.

Infrastructure strategy

Queue, Redis, and Kafka — what to buy, what to build, what to keep.

Queue system — build as designed

The repo's own Unified Job Processing design (four review rounds, "Ready for Phase 0") is the right architecture. PostgreSQL jobs table owns execution truth; Kafka owns dispatch only; Redis owns admission control. No Celery, no Temporal, no second broker. The design directly fixes the worst findings: sequential AI consumer becomes a realtime lane with bounded concurrency (8) that scales linearly; outbox drain gets FOR UPDATE SKIP LOCKED; retries get mandatory jitter; 429s become blocked state instead of lost messages.

Redis strategy

Redis is authentication infrastructure, not a cache. Rate limits, JWT blacklist, sessions, OTPs live there; auth fails closed. Target state: background prober re-arming Redis after blips, AOF enabled, 1-2 GB, memory alarm at 75%, then ElastiCache multi-AZ. Cache hot reads (LLM model registry 60s, FB profiles). Move aggregates to write path. Shared subscriber per process instead of one Redis connection per open tab. Redis must never own message content, job state, or anything that can't be lost.

Kafka usage

Keep it — for dispatch, and only dispatch. Three things are wrong today, all fixed in the approved plan: durability is theater (auto-commit offsets, acks=1 no idempotence, single broker RF=1); topics auto-created at 1 partition (zero throughput from --scale); safety net is already Postgres (outbox drain fallback means a broker outage loses nothing). What Kafka should never do here: priority, delay, or scheduling (jobs table owns all three), WebSocket fan-out (Redis), or anything request/response.
