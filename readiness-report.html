Scorecard by surface

Backend Hardened 1 high left

Architecture is right, execution has ceilings. The AI-reply path now runs on a bounded-concurrency worker with lease-based claiming (SCALE-1). Realtime inbox appends WS messages to state forever; no list virtualization anywhere. Zero automated tests. CSP is now nonce-based with strict-dynamic (SEC-M8) — no more unsafe-inline in script-src. XSS surface is genuinely clean.

Admin One app, one password

The duplicate in-web admin is gone — apps/admin is the single admin surface. One shared ADMIN_PASSWORD_HASH for all operators — no named accounts, no audit trail of who did what. Backend admin endpoints are properly gated (admin JWT type, cookie + X-Requested-With, lockout). Named operator accounts and an action audit log are still open.

Infrastructure Single box, zero DR

One t3.small (2 GB) runs API + worker + Redis + Kafka + TLS ingress. Its failure kills auth (Redis fail-closed), messaging, and ingestion simultaneously. Kafka is a single broker, replication factor 1. CI now gates every deploy on the test suite. Still open: no backup rehearsal, no prod host, and the deploy pulls a mutable :staging tag.

§§ 5

Queue system — the plan is already approved

Verdict: build it, as designed  The repo's own Unified Job Processing design (docs/specs/2026-10-10-unified-job-processing-design.md, four review rounds, final verdict "Ready for Phase 0") is the right architecture, and it answers the queue question correctly:

  • PostgreSQL jobs table owns execution truth — state machine, attempts, leases, priorities, per-tenant idempotency, and the ambiguous state from Round 4.
  • Kafka owns dispatch only — the wire carries just {"job_id"}; payloads stay in Postgres, so a broker outage loses nothing.
  • Redis owns admission control — rate windows and per-tenant in-flight caps, all reconstructible.
  • No Celery, no Temporal, no second broker. Deliberately — the design doc's reasoning holds: Sayvors' jobs are single external calls with retry, not multi-step workflows.

This design directly fixes the audit's worst findings: the sequential AI consumer becomes a realtime lane with bounded per-replica concurrency (8) that scales linearly with worker replicas; the outbox drain gets FOR UPDATE SKIP LOCKED; retries get mandatory jitter; 429s become a blocked state instead of lost messages; failures land on a replayable DLQ. The codebase already contains proof the pattern works — lead_action_worker is the one queue implemented correctly (SKIP LOCKED + lease + expired-lease release), and the design generalizes it.

Execution order (per the approved Phase 0 instructions)

  • Phase 0 — foundations. jobs table + status enum + attempt history, tenant-scoped idempotency with payload fingerprint validation, the three indexes, outbox dedupe_key (nullable UNIQUE — existing events unaffected), hard_deadline_at with SQL LEAST() clamping, job_lane_heartbeats, topic provisioning with explicit partitions, auto-create disabled. Repair the stale alembic/env.py import list first — autogenerating against it would emit spurious drops.
  • Phase 1–2 — correctness. Manual offset commits only after idempotency lands; unique indexes on platform message/comment ids; atomic enqueue_event_in(db, →→→).
  • Phase 3–4 — runtime, lane by lane. Migrate STT/TTS first (no external side effects), then publishing (crash-after-publish reconciliation), then realtime — the AI replies that are today's bottleneck.

Honest ceiling, stated by the design itself: a duplicate external call (double-posted Google review reply, double customer message) cannot be fully prevented during an in-flight provider call — only bounded to one, recorded as ambiguous, surfaced to an operator, and never auto-retried. No system that doesn't control the provider does better.

§§ 6

Redis strategy

Today: load-bearing and fragile  Redis is not a cache in this system — it is authentication infrastructure. Rate limits, the JWT blacklist, sessions, and OTPs live there, and the auth path fails closed: Redis down = nobody logs in, and blacklisted-token checks treat every token as revoked. Yet the instance is a single 128 MB noeviction box with no AOF and no alarm, and a boot-time blip permanently disables it for the process (the re-arm function has zero callers).

Target state

  • Reliability first: background prober calling mark_redis_available() (small fix, big effect); AOF enabled; 1–2 GB; memory alarm at 75%; then ElastiCache multi-AZ when spend allows. Keep noeviction — with real sizing and alarms, evicting OTP or blacklist keys is worse than erroring.
  • Fail-closed only where it earns it: keep fail-closed for the token blacklist once HA exists (15-min tokens bound the exposure anyway — fail-open with alerting is defensible before that).
  • Cache the hot reads: provider keys and model curation are a per-process overlay loaded from Postgres on boot, reloaded by the admin endpoints, and refreshed on the generation path at most every 15s; provider instances are reused. Extend the existing ig: cache pattern to FB profiles/posts. Per-request tenant context/permissions cache (per-request memo at minimum).
  • Move aggregates to the write path: the inbox's full-history GROUP BY dies when last_message_at/unread_count become columns maintained on message insert — Redis counters as the write-through, DB columns as truth.
  • Pub/sub fan-out: one shared subscriber per process dispatching to local WS clients, instead of one Redis connection per open tab — this is what makes 20–50k dashboard connections survivable on one Redis.
  • What Redis must never own: message content, job state, anything that can't be lost. The job design already encodes this — Redis holds only reconstructible counters and leases.
§§ 6b · new workstream

Billing, plans & wallet

Wallet hotfix in tree · plans not built  This is a product workstream, separate from the 21/3 audit ledger. The target is simple to state and hard to get wrong: a tenant can buy a plan without an admin, the backend activates it and grants the included AI credit, every metered AI call spends from a durable balance, and plan limits are enforced at every write path.

What broke

  • The live wallet had a 24h TTL. BUDGET_TTL_SECONDS = 86_400; sync_balance() used SETEX, and reserve()/settle() refreshed the expiry. A wallet that was not touched for a day disappeared.
  • A missing key became a permanent zero. DECRBY on a missing key creates −5; the failed reservation refunded it to 0. get_balance() then returned a present 0, so the DB fallback never fired.
  • The DB was grants-only. users.ai_credit_cents only went up; no code decremented it. llm_usage_events is fire-and-forget metering, not a spend ledger. Rebuilding from the DB column alone would hand back spent credits.
  • Some paths charged the wrong wallet. rag/agent.py and billing/router.py used user.id instead of tenant_id_of(user), creating employee-scoped ai_balance:<employee-id> keys.

Wallet — durable fix (next)

Redis remains the live counter, so a Redis loss still loses the last few seconds of spend and relies on metered usage to rehydrate. That is acceptable as a bridge, not as the billing system of record. The durable design:

  • One DB ledger entry per charge/refund — amount, tenant, model, reservation id, idempotency key, balance after, timestamp. llm_usage_events gets the cost or references the ledger row.
  • Atomic reserve/settle in Postgres — reserve locks the wallet row and checks balance ≥ amount; settle writes the actual charge and releases the difference. A hold/reaper handles crashed requests.
  • Idempotent by construction — one charge per reservation, one usage row per call, retries cannot double-apply.
  • Backfill + cutover — replay current grants and metered usage into the ledger, reconcile Redis against it, then remove the computed-reseed path.
  • Admin reconciler — compare Redis vs DB, show the delta, repair with an audit row; never accept a client-supplied balance.

Activation — one function, three sources

activate_subscription(tenant_id, plan_id, source, period_start, period_end, provider_event_id=None) is the only writer of an active subscription. It:

  • closes/expires the previous active subscription for that tenant;
  • inserts the new subscription with source ∈ {demo, admin, payment};
  • writes the plan's included credit as a real billing/ledger event;
  • syncs the Redis cache only after the DB commit.

Demo Pro is a server-side source, not a client flag. The endpoint is admin-gated and behind BILLING_DEMO_MODE; production returns 404/403 when the flag is off. The payment webhook uses the same function, keyed by provider_event_id so retries are idempotent. Admin assignment remains for support, but it is visibly logged as an override.

Entitlements enforcement

  • Google locations: enforce in localith/router.py:save_connection and the native Google OAuth callback in channels/router.py; the callback must stop creating every discovered location.
  • Social accounts: enforce in channels/service.py:create_channel, channels/meta/service.py:select_assets, and webhook auto-create paths. Count across providers, not per provider — one WhatsApp plus one Instagram is two, not one each.
  • Atomic check-and-insert: take a transaction-scoped advisory lock keyed by (tenant, limit_key) or lock the tenant's subscription row, re-count, then insert. A plain count-then-insert is a race at two workers.
  • Downgrade: never delete data. Existing over-limit locations/accounts stay visible and read-only; new additions are blocked with a structured plan_limit_reached error and an upgrade path. The UI shows which items are over limit.
  • AI gate: check active trial/paid subscription first, then the wallet. A free tenant with leftover credit must not keep using AI after the trial.

Self-subscribe and UI

  • apps/web (customer): current plan, renewal date, credit remaining, usage meters, upgrade/downgrade, checkout return state, and a limit banner with a direct upgrade CTA. No admin controls.
  • apps/admin (platform): plan catalog CRUD, subscription overrides, demo activation, wallet preview/resync, and an audit view of who changed what.
  • Checkout: POST /billing/subscribe creates a provider checkout session; the browser returns to a success page that polls the subscription; the webhook is the source of truth. The provider choice is still open (the current gateway is a dev stub), so the webhook adapter is the only provider-specific code.
  • Portal: cancel-at-period-end, update card, invoices. Cancellation keeps access to current_period_end, then moves to expired; it does not delete data.

Order of work

  1. Wallet hotfix — in tree; run the admin resync for affected tenants and watch for rehydrate warnings.
  2. DB spend ledger — schema, atomic reserve/settle, holds/reaper, idempotency, backfill, reconciler. Remove the computed-reseed path only after the ledger is live.
  3. Plans/subscriptions/entitlements — tables, seed Starter/Pro, one activation function, central entitlements service.
  4. Demo Pro + limits — server-side demo mode, Google/social enforcement at every write path, structured upgrade errors.
  5. Customer + admin UI — plan card, usage, upgrade, limit banners; admin catalog/resync/audit.
  6. Real checkout — provider adapter, webhook, idempotency, invoices/portal. This is the only step blocked on the provider decision.

Acceptance: deleting the Redis key does not change the tenant's true balance; a re-run of resync is idempotent; a top-up never re-grants spent credit; demo Pro cannot activate in production; a second Google location or second social account is rejected atomically on Starter; a downgrade preserves data; and a paid webhook activates the plan and grants credit without an admin.

§§ 7

Kafka usage

Keep it — for dispatch, and only dispatch  Kafka is already deployed and carrying three domains (meta-events, review-events, auth-events). The approved design uses it correctly: a durable dispatch log, not a job store. Three things are wrong with it today, all fixed in the approved plan:

  • Durability is theater right now: consumers auto-commit offsets (at-most-once — crashes silently drop work), producers run acks=1 without idempotence, and there's a single broker at replication factor 1. Phase 1 fixes the client config; the broker question is below.
  • Topics were auto-created at 1 partition — --scale worker=N buys zero throughput today. Phase 0 provisions explicit partitions (24/12/6/6 per lane) keyed by tenant_id (publishing by listing_id for ordering) and disables auto-create.
  • The real safety net is already Postgres: both consumers have a DB-outbox drain fallback. That fallback — not Kafka — is why the design can honestly say a broker outage loses nothing. Until you run 3 brokers with min.insync.replicas=2, treat Kafka as an optimization over the outbox, which is exactly how the design treats it.

What Kafka should never do here: priority, delay, or scheduling (the jobs table owns all three), WebSocket fan-out (Redis), or anything request/response. If a future feature "needs Kafka," check it isn't actually asking for the jobs table.

§§ 9

What the audit found solid

  • Tenant isolation: clean bill. An adversarial pass across channels, inbox, leads, reviews, notifications, posts/media, team, storage, and RAG found no missing tenant filter. Webhook tenant resolution comes from a server-side asset registry, never payload-supplied ids.
  • Auth internals: bcrypt-12, refresh rotation with family-wide reuse detection (token reuse revokes every session), device binding, revocation generations, OTP brute-force budgets, Google/FB identities verified server-side.
  • Webhooks: HMAC verification fail-closed over the raw body before parsing; DB-level delivery dedupe.
  • A real SSRF guard exists (fetch_pinned: resolve-once, pin, re-validate every redirect) — the gaps are places that don't use it yet, not a missing primitive.
  • Uploads: magic-byte sniffing incl. polyglot rejection; traversal-guarded storage keys.
  • Frontend hygiene: zero dangerouslySetInnerHTML, a hand-rolled safe markdown renderer, every target="_blank" carries noopener, a tiny dependency tree, strict TS build gate.
  • The job design document itself is enterprise-grade — four review rounds, honest limits stated, and it anticipated most of this audit's queue findings.
